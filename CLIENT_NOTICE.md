# Security Notice — PHP CVE-2026-109618 / CVE-2026-109619

Bilingual notice (EN / IT), publication-ready.
Issued 21 October 2026. Free to reuse and redistribute with attribution.

---

## English version

**Subject: [URGENT] Critical PHP vulnerability — update now, or apply the changes below immediately**

On 21 October 2026 PHP released fixes for two vulnerabilities rated
"Critical" (CVE-2026-109618 / CVE-2026-109619, CVSS 9.2) that allow
anyone, without an account or password, to take control of the server
hosting the website. They affect PHP itself, before the website's code
even runs: they do not depend on the CMS, plugins or weak passwords,
only on the PHP version in use. Technical details are already public:
expect large-scale automated exploitation attempts in the coming days.

Every PHP version older than 8.2.35 is vulnerable. PHP 8.1 and older
are end-of-life: they will NEVER receive the official fix from PHP.

There are two ways forward, in order of preference.

**PATH 1 — UPDATE PHP (the complete fix, do it now)**

Update PHP to version 8.2.35, 8.3.36, 8.4.27 or 8.5.12 (or later).
This is a maintenance update, free of charge, that does not change
how the website works.

Who has to do it: whoever manages the hosting.

- If you have a hosting control panel (Aruba, Register, SiteGround,
  cPanel, Plesk, etc.): open the panel, go to the PHP version section,
  and select 8.3 or 8.4 (or the newest available). If the panel does
  not offer anything newer than the current version, open a ticket
  with the provider immediately and ask for a patched PHP version:
  that is their responsibility.
- If the website runs on your own server, or on a server managed by
  your technical provider: update PHP to the latest release packages
  (vendors have already shipped the fixes) and restart the PHP
  service.

If updating requires time or compatibility checks, do NOT wait:
apply Path 2 right away and complete Path 1 as soon as possible.

**PATH 2 — IF YOU CANNOT UPDATE IMMEDIATELY: CHANGES TO APPLY**

These changes strongly reduce exposure but do not completely close
the vulnerability: they are a bridge towards Path 1, not a definitive
solution.

*2a) Disable the affected PHP feature (the most important one)*

In the php.ini file (or in the PHP-FPM pool / Apache configuration,
NEVER inside the website's code) add:

    session.upload_progress.enabled = 0

then restart PHP (or ask whoever manages the server to do it). This
feature is only used to show upload progress bars: the vast majority
of websites do not use it and will notice no difference. IMPORTANT:
it must be set in php.ini or in the server configuration, NOT via
ini_set() in the code and NOT in the .user.ini file: in those ways it
has no effect against this vulnerability.

*2b) Limit the size of requests*

Still in php.ini:

    post_max_size = 8M

If the website MUST receive file uploads (images, documents, import
files), use 32M instead of 8M, and keep upload_max_filesize lower
than post_max_size.

*2c) Limit the amount and complexity of incoming data*

Still in php.ini:

    max_input_vars = 3000
    max_input_nesting_level = 32
    max_file_uploads = 20

(increase max_file_uploads only if the website has forms with many
simultaneous uploads).

*2d) If a firewall, proxy or CDN sits in front of the website
(e.g. Cloudflare)*

Block or throttle "multipart/form-data" POST requests towards the
public pages of the website that are not used for file uploads, and
enforce a maximum request body size, valid also for requests without
a declared length.

*2e) Configuration cleanup*

Whoever manages the server should remove any deprecated or invalid
PHP settings in configuration files applied to individual requests
(.htaccess with php_value, PHP_VALUE passed to FPM): every warning
generated by those settings is a foothold for the attack. Hiding the
warnings (error_reporting, display_errors) does NOT help.

**AFTER THE CHANGES**

Ask whoever manages the server to confirm the values are active (a
protected phpinfo() page, or provider verification) and that PHP has
been restarted. The changes only take effect after the restart.

Public references: php.net (announcement of 21 October 2026) and
advisories GHSA-w8hw-w9fx-j79w / GHSA-6wmf-4rv5-p3rp on
github.com/php/php-src.

## Versione italiana

**Oggetto: [URGENTE] Vulnerabilità critica di PHP — aggiornare, oppure applicare subito le modifiche sotto**

Il 21 ottobre 2026 PHP ha corretto due vulnerabilità classificate
"Critical" (CVE-2026-109618 / CVE-2026-109619, punteggio 9.2) che
permettono a chiunque, senza account né password, di prendere il
controllo del server che ospita il sito. Colpiscono PHP stesso, prima
che il codice del sito venga eseguito: non dipendono dal CMS, dai
plugin o da password deboli, ma solo dalla versione di PHP in uso.
I dettagli sono già pubblici: nei prossimi giorni ci aspettiamo
tentativi automatici su larga scala.

Tutte le versioni di PHP precedenti a 8.2.35 sono vulnerabili. Le
versioni 8.1 e precedenti hanno terminato il supporto: NON riceveranno
mai la correzione ufficiale da PHP.

Le strade sono due, in ordine di preferenza.

**STRADA 1 — AGGIORNARE PHP (soluzione completa, da fare subito)**

Aggiornare PHP alla versione 8.2.35, 8.3.36, 8.4.27 o 8.5.12 (o
successiva). È un aggiornamento di manutenzione, gratuito, che non
cambia il funzionamento del sito.

Chi lo deve fare: chi gestisce l'hosting.

- Se avete un pannello di hosting (Aruba, Register, SiteGround, ecc.):
  entrate nel pannello, sezione PHP / versione PHP, e selezionate
  8.3 o 8.4 (o l'ultima disponibile). Se il pannello non offre niente
  di più recente della versione attuale, aprite subito un ticket al
  provider chiedendo una versione PHP corretta: è una loro
  responsabilità.
- Se il sito è su un server vostro o di un vostro gestore tecnico:
  aggiornate PHP ai pacchetti dell'ultima release (i vendor hanno già
  distribuito le correzioni) e riavviate il servizio PHP.

Se aggiornare richiede tempi o verifiche di compatibilità, NON
aspettate: applicate subito la Strada 2 e concludete la 1 il prima
possibile.

**STRADA 2 — SE NON POTETE AGGIORNARE SUBITO: MODIFICHE DA APPLICARE**

Queste modifiche riducono fortemente l'esposizione ma non chiudono
completamente la vulnerabilità: sono un ponte verso la Strada 1, non
una soluzione definitiva.

*2a) Disattivare la funzione PHP incriminata (la più importante)*

Nel file php.ini (o nel pool PHP-FPM / configurazione Apache, MAI
dentro lo script del sito) aggiungere:

    session.upload_progress.enabled = 0

poi riavviare PHP (o chiedere il riavvio a chi gestisce il server).
Questa funzione serve solo per mostrare la barra di avanzamento dei
caricamenti: la stragrande maggioranza dei siti non la usa e non
noterà alcuna differenza. IMPORTANTE: va messa nel php.ini o nella
configurazione del server, NON tramite ini_set() nel codice e NON
nel file .user.ini: in quei modi non ha effetto su questa
vulnerabilità.

*2b) Limitare la dimensione delle richieste*

Sempre nel php.ini:

    post_max_size = 8M

Se il sito DEVE ricevere caricamenti di file (upload immagini,
documenti, import), usare 32M invece di 8M, e tenere
upload_max_filesize inferiore a post_max_size.

*2c) Limitare il numero e la complessità dei dati in ingresso*

Sempre nel php.ini:

    max_input_vars = 3000
    max_input_nesting_level = 32
    max_file_uploads = 20

(aumentare max_file_uploads solo se il sito ha form con più upload
simultanei).

*2d) Se davanti al sito c'è un firewall, proxy o CDN (es. Cloudflare)*

Bloccare o limitare le richieste POST di tipo "multipart/form-data"
verso le pagine pubbliche del sito che non servono per caricamenti di
file, e far rispettare un limite massimo alla dimensione del corpo
delle richieste, valido anche per le richieste senza lunghezza
dichiarata.

*2e) Pulizia della configurazione*

Chi gestisce il server deve rimuovere eventuali impostazioni PHP
deprecate o non valide nei file di configurazione applicati alle
singole richieste (.htaccess con php_value, PHP_VALUE passati a FPM):
ogni avviso generato da quelle impostazioni è un punto d'appoggio
dell'attacco. Nascondere gli avvisi (error_reporting, display_errors)
NON serve.

**DOPO LE MODIFICHE**

Farsi confermare da chi gestisce il server che i valori sono attivi
(chiedete una pagina phpinfo() protetta o la verifica dal provider)
e che PHP è stato riavviato. Le modifiche valgono solo dopo il
riavvio.

Riferimenti pubblici: php.net (annuncio del 21/10/2026) e gli advisory
GHSA-w8hw-w9fx-j79w / GHSA-6wmf-4rv5-p3rp su github.com/php/php-src.
